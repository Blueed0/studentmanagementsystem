## 2. Task 1 – Requirements Analysis

### 2.1 Problem

University staff need a simple tool to register students, create courses, enroll students without duplicates, calculate how many courses each student takes, and display students by degree program together with the enrollment list.

### 2.2 Stakeholders

- Academic office staff
- Advisors checking student course load
- Assessors reviewing OOP design and rejected operations

### 2.3 Functional requirements

1. Register bachelor and master students with unique Ids, name, age and degree program.
2. Create courses with unique codes, titles and strictly positive capacity.
3. Enroll a student in a course at most once.
4. Calculate and show the number of courses for a student.
5. Display students by program and display the enrollment list.
6. Reject invalid input and unknown identifiers without corrupting stored data.

### 2.4 Unique identifiers

- Student Id (example: `S1001`)
- Course code (example: `CS101`)
- Enrollment Id generated by the system

### 2.5 Business rules

**Rule A – Age range.** Age must be between 15 and 65 inclusive.  
**Rule B – Enrollment constraints.** A student may enroll in a course only once, and a course cannot accept more enrollments than its capacity.

### 2.6 Success and rejection

Successful operations add valid objects to the in-memory lists. Rejected operations throw a clear exception before mutating those lists, so failed enrollments or duplicate Ids do not change system state incorrectly.

## 3. Task 2 – UML Diagram

The UML class diagram is in `docs/UML_CLASS_DIAGRAM.md`. It includes more than five meaningful classes: `IIdentifiable`, `Student`, `BachelorStudent`, `MasterStudent`, `Course`, `Enrollment` and `UniversityManager`.

`BachelorStudent` and `MasterStudent` inherit from abstract `Student`. `Student` and `Course` realize `IIdentifiable`. `Enrollment` associates one student with one course. `UniversityManager` owns the collections and applies the business rules. The diagram matches the implementation.

---

## 4. Task 3 – C# Implementation Overview

The prototype is a .NET 8 console application. Private fields are exposed through validated properties and constructors. Inheritance and polymorphism appear in the student hierarchy through `GetAcademicLevel()` and `GetStudentDetails()`. Association is represented by `Enrollment`. The console UI calls `UniversityManager` instead of editing lists directly. `IIdentifiable` provides a shared Id contract, and abstract `Student` forces an academic level to be chosen.

Menu options map directly to the case requirements: register, create course, enroll, calculate courses of a student, display students by program, and display the enrollment list. Listing all students is kept only to demonstrate polymorphic details during defense.

## 6. Task 5 – Design Justification and Comparison

### 6.1 Responsibilities

`Student` subclasses store personal academic data. `Course` stores capacity. `Enrollment` stores the relationship. `UniversityManager` applies cross-object rules. `Program` handles console input and output only.

### 6.2 Abstraction and polymorphism

Abstract `Student` keeps shared validation in one place. Listing students calls `GetStudentDetails()` on a `Student` reference, and the runtime selects bachelor or master formatting.

### 6.3 Comparison

A procedural version would repeat validation in many menu branches and would be easier to break. A scripting approach can automate input, but models relationships weakly. The OOP design localizes invariants next to the data they protect.

### 6.4 Limitation and improvement

**Limitation:** Data is stored only in memory and disappears when the program exits.  
**Improvement:** Persist the same domain classes to a file or database later without changing the OOP model.
