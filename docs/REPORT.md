## 1. Introduction

This report documents the design and implementation of a console-based Student Management System developed as a midterm Object-Oriented Programming case study. The system supports registration of bachelor and master students, creation of courses, enrollment management, searching, listing, and safe removal of records. The solution deliberately stays within the weeks 1–6 scope: classes and objects, encapsulation, inheritance, association, interfaces or abstract classes, polymorphism, collections, and functional testing. No database, GUI, website, or API was used.

The purpose of the prototype is to show that business rules can be expressed as class responsibilities and validated operations rather than as a flat sequence of scripts. All sample data used in the application is fictional. The project also prepares the team for individual oral defense by keeping every rule visible in code and documentation, so that any member can explain not only what the menu does, but why a rejected operation leaves the system unchanged.

From a learning perspective, Case 01 is valuable because it combines identity management, capacity control, and association in one coherent domain. Students are not merely records; they specialize into bachelor and master profiles. Courses are not merely titles; they constrain enrollment. The association object makes those constraints observable and testable.

## 2. Task 1 – Requirements Analysis

### 2.1 Problem description

A university office needs a lightweight tool to manage students and course enrollments during planning and demonstration sessions. Staff must register students with unique identifiers, define courses with limited seats, enroll students without duplicates, calculate how many courses each student takes, and display students belonging to a given degree program together with the enrollment list.

### 2.2 Stakeholders

- Academic office staff who register students and courses
- Advisors who check a student’s course load
- Course coordinators who inspect a course roster
- Assessors who verify OOP design quality and rejected-operation behavior

### 2.3 Functional requirements

1. Register bachelor and master students with unique Ids, full name, age, and degree program.
2. Create courses with unique codes, titles, and strictly positive capacity.
3. Enroll a student in a course at most once.
4. Calculate and display the number of courses for each student.
5. Display students filtered by degree program and display the enrollment list.
6. Support search, drop enrollment, and safe removal when no dependent enrollments remain.
7. Reject invalid input and unknown identifiers without corrupting stored data.

### 2.4 Unique identifiers

- Student Id (for example `S1001`)
- Course code (for example `CS101`)
- Enrollment Id generated by the system (for example `ENR-0001-153045`)

### 2.5 Business rules

**Rule A – Age range.** A student’s age must be between 15 and 65 inclusive. Values outside this range are rejected during construction through property validation.

**Rule B – Enrollment constraints.** A student may enroll in a course only once; a course cannot accept enrollments beyond its capacity; a student may take at most five courses at the same time.

### 2.6 Success and rejection behavior

When an operation succeeds, the corresponding object is created or updated in the in-memory collections managed by `UniversityManager`, and the console shows a success message. When an operation is rejected, an exception with a clear English message is thrown before any mutating list change occurs for that operation. As a result, failed enrollments do not add partial rows, and duplicate Ids do not overwrite existing students or courses.

This success-or-reject model is important for assessment because it turns validation into observable behavior. Testers can compare expected and actual messages, then confirm counts for students, courses, and enrollments. The same pattern also protects demonstration sessions: entering a wrong age or unknown Id does not leave the prototype in an inconsistent state that would confuse later menu options.

## 3. Task 2 – UML Diagram and Flowcharts

The UML class diagram is provided in `docs/UML_CLASS_DIAGRAM.md` and can be viewed visually in `docs/diagrams.html`. It contains more than five meaningful classes: `IIdentifiable`, `Student`, `BachelorStudent`, `MasterStudent`, `Course`, `Enrollment`, and `UniversityManager`, with `Program` as the console entry point. Behavioral flowcharts for the main menu, registration validation, and enrollment decision rules are provided in `docs/FLOWCHART.md` so that structure (UML) and runtime process (flowchart) are both documented.

The model uses inheritance from abstract `Student` to `BachelorStudent` and `MasterStudent`. Both `Student` and `Course` realize `IIdentifiable`. `Enrollment` associates one student with one course and stores the enrollment date. `UniversityManager` owns the collections and exposes validated CRUD-style operations. Access modifiers in code match the diagram: private backing fields, public properties with validation, and protected or public constructors where appropriate. Multiplicities follow the business rules: a student may have zero to five enrollments, and a course may have zero to capacity enrollments.

Consistency between UML and code was treated as a quality requirement, not as decoration. Every attribute shown in the diagram has a corresponding field or property, and every major operation used in the defense scenario appears as a method on `UniversityManager` or on a domain class. If the diagram claimed a relationship that the code did not implement, the team would have either updated the diagram or changed the implementation. In the final package they match.

## 4. Task 3 – C# Implementation Overview

The prototype is a .NET 8 console application. Encapsulation is applied consistently: private fields are exposed through properties that validate emptiness, ranges, and null references. Constructors trigger those setters so invalid objects cannot be created quietly.

Inheritance and polymorphism appear in the student hierarchy. `GetAcademicLevel()` is abstract and overridden by bachelor and master subclasses. `GetStudentDetails()` is virtual and extended so listing students automatically shows study year or thesis topic without `if`-type branching in the UI.

Composition and association are represented by `Enrollment`, which keeps live references to `Student` and `Course` objects. The console never manipulates the internal lists directly; all rules are centralized in `UniversityManager`. This separation keeps UI code focused on input and output while the service layer protects invariants such as uniqueness, capacity, and maximum course load.

At least one meaningful interface is present: `IIdentifiable` requires a read-only `Id`. Abstract `Student` also prevents creating a generic student without choosing an academic level, which matches the domain.

Implementation details that support maintainability include returning copies of lists from getter-style manager methods, using case-insensitive Id comparison for practical console use, and generating readable enrollment identifiers. Sample seed data is loaded at startup so a live demonstration can begin with existing students and enrollments, then still allow interactive creation of new records. Menu option 14 was added specifically to satisfy the case requirement to display students by degree program, complementing the full enrollment list already available in the menu.

## 5. Task 4 – Testing

At least eight documented cases are recorded in `docs/TEST_CASES.md`, exceeding the required minimum of six. The suite includes normal paths, invalid input, duplicates, unknown identifiers, and boundary conditions.

Representative findings:

- Valid bachelor registration increases the student count and appears in listings.
- Age 14 or 66 is rejected; age 15 is accepted as an inclusive boundary.
- Reusing student Id `S1001` is rejected and leaves the original record unchanged.
- Duplicate enrollment of the same student into the same course is rejected.
- When course capacity is exhausted, further enrollments are rejected and the enrollment count does not rise.
- Viewing a student’s courses shows the calculated load, and filtering by program returns only matching students.

In every unsuccessful case, the actual message matched the expected rejection text, and system state was preserved. This satisfies the assessment requirement to verify that failed operations do not incorrectly change stored data.

Testing was approached as functional evidence rather than as automated unit-test infrastructure, which is appropriate for a console prototype in the weeks 1–6 scope. Each case records preconditions, inputs, expected result, actual result, and PASS/FAIL. Boundary tests were prioritized because inclusive ranges are easy to implement incorrectly. Likewise, duplicate and unknown-Id cases prove that lookup failures are handled explicitly instead of failing with unclear runtime errors.

## 6. Task 5 – Design Justification and Comparison

### 6.1 Class responsibilities

`Student` and its subclasses own personal academic identity data. `Course` owns capacity. `Enrollment` owns the relationship and timestamp. `UniversityManager` owns orchestration and cross-object rules. `Program` owns interaction only. This distribution avoids a single “god script” and makes oral defense easier because each rule has a clear home.

### 6.2 Abstraction and polymorphism

Abstract `Student` captures common validation once. Polymorphism lets the list screen call `GetStudentDetails()` on a `Student` reference while the runtime selects bachelor or master formatting. That is preferable to scattering type checks through the menu handlers.

### 6.3 Comparison with procedural and scripting approaches

A purely procedural version would store parallel arrays or loosely related variables and repeat validation in many menu branches. It can work for tiny demos, but duplicate checks and capacity logic quickly drift out of sync. A scripting approach can automate input quickly, yet it usually under-models relationships and offers weaker compile-time structure for inheritance and interfaces. The OOP solution is more verbose at first, but it localizes invariants next to the data they protect and makes rejected operations explicit through exceptions.

### 6.4 Limitation and realistic improvement

**Limitation:** All data lives in memory and disappears when the process exits.  
**Realistic improvement:** Persist collections to a simple file or database while keeping the same domain classes and validation, without changing the OOP design of the core model.

Another possible improvement is richer reporting, such as sorting students by course load, still using the existing manager methods. A further improvement could introduce soft-delete or archive behavior for historical enrollments, provided the same uniqueness and capacity rules remain enforceable for active records.

Overall, the OOP design is justified because the domain naturally contains specialization, shared identity, and many-to-many style participation through an association class. Those structures are awkward to keep correct in a purely procedural listing of steps, especially when rejection must leave prior data intact.

## 8. Conclusion

The Student Management System meets Case 01 functional expectations and the six common assessment tasks. It implements the suggested class set, enforces unique identifiers and enrollment constraints, calculates course counts, displays students by program and enrollment lists, and documents successful and unsuccessful tests. The design applies encapsulation, inheritance, association, abstraction, and polymorphism in a console prototype suitable for defense.

The main achievement is not only that the menu works, but that the working behavior is explained by an OOP model whose responsibilities can be defended line by line. With the accompanying UML, tests, and statements, the package is ready for report submission and individual oral examination.
